## Storage and consent decisions

Native authentication uses Keychain-backed SecureStore; health cache/outbox use app-local storage/SQLite. The new native plugin excludes Documents and Application Support from backup before React starts and sets AsyncStorage's backup-exclusion option. It fails closed if native directory protection cannot be set. This is prepared source, not proof about existing installed builds, historical backups or every future SDK path. Local records do not gain application-level end-to-end encryption from this change.

Browser preview uses localStorage for account/session and functional persistence, with weaker protection than Keychain; it is not an approved production web application. Prepared standalone legal HTML has no storage or scripts. No embedded website or tracking pixel was found. There is therefore no observed advertising/analytics processing for a consent banner to gate. UK/EU storage rules still require purpose-by-purpose review if launched there: necessary authentication/preferences may qualify for exemptions; it is not valid to exempt every future local write by calling it native. [ICO storage guidance](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guidance-on-the-use-of-storage-and-access-technologies/what-are-storage-and-access-technologies/).

Privacy notice, contractual agreement, AI-processing choice, OS permission and ATT are separate concepts. No mandatory blanket checkbox was added. Meal requests require a fresh off-to-on choice after each attempt, including errors/cancellation. Workout planner permission/history switches start off when opened. Declining leaves manual logging available; cancelling after transmission only stops the client from accepting a late result. Leaving/reopening the planner resets its choice; no enduring AI-enable preference authorizes future requests. Delete saved planner data removes cloud preferences/conversations and this device's saved planner preferences, not existing health logs, local workout drafts, provider-held copies, usage counters or minimal receipts. An already in-flight/new request on another device could create new planner data; this control is not global account deletion or a provider erasure request.

## Export, correction and deletion coverage

The export now includes profile/auth metadata, vitals, workouts/sets, cardio, nutrition, fluids/saved drinks, food profiles/recipes, photo metadata, coach profiles/threads/messages/actions, onboarding state, streak rules/goals/activation and legacy food-day flags, AI receipts/usage, this device's reminders/completions/drafts/HealthKit state/vital cache, plus allowlisted layout/routine/helper/retry state. Optional photo archive streams native files. Stable ordering uses each table's actual keys rather than assuming every table has `id`. Account assertions surround collection, pagination and archive sharing; CSV formula prefixes are escaped. Missing required tables/grants cause an explicit incomplete-export failure, not a falsely complete file.

This is not an atomic database snapshot: concurrent edits can affect pagination. A full export still accumulates structured rows in memory; large accounts need future streaming/snapshot design. It does not export other devices' offline-only data, provider infrastructure logs, authentication secrets, deletion capabilities or service-only security/consistency tables. Handle legally required supplemental access through a verified privacy request with secrets and other people's data excluded. Do not claim the self-service archive is every record a provider might hold.

History/profile provide manual-record and goal correction. Imported measurements are source-aware/read-only for correction; originals are managed in Apple Health. Individual vital deletion keeps a synchronization tombstone; progress-photo deletion uses a durable retry for storage cleanup. Account deletion prepares a server write barrier under an advisory lock, revokes sessions/device credentials, deletes private storage and Auth with cascades, verifies completion and clears this device's local state/cache. A recovery capability can resume after authentication has been removed. The new AI receipt table receives the same write guard and cascade. Source/database tests cover stale service writes and account isolation; a hosted end-to-end synthetic deletion test is still required after authorized rollout.

## Practical operating procedures

**Ownership and request intake.** Before release assign a privacy/security owner and monitored support/privacy addresses. Start requests with account email, request type and relevant jurisdiction only; never request a password, full health export or government ID by default. Prefer in-app authenticated action or a one-time verification to the existing verified account. Track receipt, verification, scope, statutory deadline, vendors contacted, completion and any appeal. Apply the shortest relevant deadline; set an internal two-business-day acknowledgment and initial review target of 30 days as proposed operating goals, not invented statutory limits. Health-data requests may need a different deadline/extension rule. Send results through authenticated export or a short-lived protected delivery method, not an ordinary attachment to an unverified address. No real mailbox or ticket workflow was configured here.

**Incidents.** Preserve minimal access-controlled evidence; stop the affected disclosure/path, rotate compromised credentials, revoke sessions and involve providers. Assess affected people/data/time range and whether unauthorized acquisition or disclosure occurred, including an unintended AI/analytics transmission. Determine FTC HBNR, state breach and any other notification obligations with counsel. HBNR consumer notice generally must occur without unreasonable delay and within 60 calendar days; FTC timing differs for breaches affecting at least 500 people versus smaller annual reports, and media notice can apply at 500 residents in a state/jurisdiction. Do not wait for those outer limits to start response. Additional applicable laws may be faster. Test the process with a synthetic incident and document decisions without copying private payloads into issue trackers. [FTC response guidance](https://www.ftc.gov/business-guidance/resources/complying-ftcs-health-breach-notification-rule-0).

**Provider review.** Record service/contract owner, exact purpose/categories, subprocessors/locations, access controls, retention settings, deletion/export support, incident contact and contractual role. Review Supabase and OpenAI account-specific agreements; determine whether a health-data processor relationship or special authorization is required in launch states. A public marketing statement is not a signed DPA or verified production configuration. No provider contracts were accepted by this task.

**Retention schedule.** Saved records/drafts presently persist until the user acts; do not invent an automatic expiry. Temporary photo intermediates and export ZIPs now have best-effort immediate cleanup on the normal path; process termination can leave cache. Quotas, tombstones and receipts do not have a comprehensive scheduled purge. Proposed owner decisions: shortest supported diagnostic retention (target 30 days or less), bounded security evidence, and a documented backup window. Before pruning any tombstone/receipt, design maximum supported offline/retry age or a resynchronization epoch so deletion/idempotency cannot regress. Schedule privacy-preserving orphan-photo reconciliation with a grace period and active-upload checks. These jobs are recommendations awaiting design/approval, not deployed features. Until decided, drafts accurately flag operational retention as unresolved.

**Backups and restoration.** Verify an actual backup/restore arrangement before taking public users. Supabase documents daily backups for paid plans and recommends separate exports for Free projects; database backups do not contain Storage object bytes. Therefore do not promise either a specific retention window or recoverable photos merely because the database is hosted. [Supabase backup documentation](https://supabase.com/docs/guides/platform/backups).

Restore into an isolated environment first. Keep a protected deletion ledger outside the restored snapshot, with only the identifiers needed to reapply removals and a justified retention period. Reapply account/record/file deletions and revocations, reconcile photo metadata/objects and validate write guards before enabling traffic. Revoke restored sessions/device credentials where necessary. Verify with synthetic deleted and retained accounts and record results. The independent ledger/restore exercise does not yet exist; this is a release blocker rather than a policy promise.

**Change management.** For every country, SDK, AI provider/tool, data category, monetization or claim change: update inventory and threat review; assess legal scope; revise purpose strings/disclosures and App Privacy answers; bump AI notice version if covered sharing changes; coordinate server/client rollout; retain approved policy versions and effective dates. Re-run synthetic privacy and accessibility journeys and archive checks. Recheck published host behavior, support routing and current official requirements immediately before submission and after material changes.
