# ADR-009: Device-local routine reminders and coordinated notifications

Date: 2026-09-22
Status: Implemented locally; physical-iPhone delivery and accessibility validation pending.

## Product and persistence

Reminders now separates Meals, Fluids, Blood Pressure, Weight and Workout routines from the existing custom definitions and completion history. Routine master/category switches start off. First activation selects categories, reviews editable local times and notification counts by weekday, then requests permission. Permission denial retains settings and offers Open Settings; the native adapter requests only when permission is undetermined and canAskAgain is true. Returning from Settings reconciles with current permission.

Preferences use the validated account-scoped `healthapp:routines:v1:<user>` key. Saved choices are never reseeded. Quiet hours default to 22:00–07:00 and apply only to routines. Conflicts require changing the chosen time or quiet window before activation; equal start/end means all-day quiet. Within-category duplicate times block activation; simultaneous cross-category times produce a notice. Workout days are deliberately unselected initially. Defaults are conveniences, not personalized recommendations.

Existing custom data stays in its original repository. Device request identifiers/status use separate v2 keys. Legacy identifiers remain readable for migration and cleanup. Strict reads reject wrong-account/corrupt definitions instead of overwriting them with defaults. No schema, server function, dependency or hosted deployment change is needed.

Only structured BP/weight kind, time and weekday overlap offers Keep custom / Replace / Keep both. Medication names are never duplicate heuristics. Replacement intent is saved first, and the old custom reminder is disabled only after the routine requests are confirmed by the native pending-request API. History survives. Blocked permission or native failure leaves the custom enabled. Routine preferences and notification taps never enter custom completion lists, reminder denominators, health repositories or goal-streak writes.

## Scheduling and capacity

One serialized service owns routine/custom reconciliation, activation, explicit logout and deletion. Requests have deterministic account/source/group/slot IDs; dated requests also include their local occurrence day. Fingerprints cover content, intent and trigger. The OS pending list is authoritative, including other-account custom requests when counting capacity.

| Schedule | Native iOS trigger | Unopened-app behavior |
| --- | --- | --- |
| Stable daily/custom multiple-daily or all-week routine | Repeating calendar hour/minute | Continues without a JS process or rolling replenishment |
| Selected weekdays | One repeating calendar request per time/weekday | Continues without reopening |
| Workout | Nonrepeating calendar request per selected day in the next 28 local calendar days | Stops at the end of the saved window; foreground/login/edit replenishes it; UI shows the scheduled-through date |
| Custom one-off | One nonrepeating calendar request | Existing single occurrence only |
| Custom future start or early completion of today's upcoming slot | Next 14 valid occurrences as nonrepeating calendar requests | Requires foreground reconciliation to extend the window or return to native repeats; this is 14 occurrences, not necessarily 14 days |

The custom exception preserves start-date and early-completion semantics rather than sending a completed upcoming prompt or starting before the chosen date. It can consume more capacity. Stable custom medication schedules cannot disappear merely because frequent routine occurrences occupy an earlier part of a shared next-60 list.

The desired total is limited to 60 pending requests across the app; four additional slots are reserved for verified add-before-remove transitions. Native repeating requests count once per request, not once per future delivery. [Apple's legacy UILocalNotification documentation](https://developer.apple.com/documentation/uikit/uilocalnotification) states a 64-request limit; the current UserNotifications scheduling documentation does **not** publish a guaranteed numeric ceiling. Therefore 60 is a conservative application budget, not a claim that a modern iOS limit has been measured. Actual capacity/retention must still be verified on the target iPhone.

Explicit off/delete choices cancel their own requests before attempting an unrelated rebuild, so a capacity failure cannot leave a disabled routine active. Capacity is checked before adding or replacing enabled schedules. Custom groups migrate first: add or replace requests using stable identifiers, read back and verify all members of that group, then remove its obsolete requests. This lets a full legacy 60-request window shrink before routines are added. Other groups remain working if a later group fails. Unknown legacy ownership or a group requiring more transition slots than available produces an actionable error and preserves its existing requests. Final verification checks that no obsolete owned requests remain. Retrying is idempotent and recovers successful partial additions. There is no cancel-all/rebuild operation and no silent truncation to fit capacity.

Saving definitions and scheduling are intentionally separate: settings remain saved on permission denial or OS failure, with a visible blocked/error state and Retry scheduling. "Scheduled" is shown only after confirmed routine requests. A failed update can temporarily leave an older schedule or a partially applied new schedule; the screen does not claim successful synchronization. Explicitly disabling/deleting while permission is revoked still cancels obsolete requests, including archived legacy IDs.

## Local time, DST and suppression

All native inputs use calendar components without a fixed `timezone`. Daily/weekly triggers contain hour/minute/second and optional native weekday (Sunday=1). Dated requests contain year, **1-based calendar month**, day and time. The installed Expo 57 parser/Swift `CalendarTriggerRecord` was inspected: calendar components pass through to `UNCalendarNotificationTrigger`; the distinct monthly/yearly helper input conventions are not used here.

The intended behavior follows device wall-clock time, including after travel. Foreground reconciliation rebuilds dated requests in the current zone. Workout dates advance with local calendar constructors, never fixed 24-hour increments. A nonexistent spring-forward workout time is skipped, not silently moved; fall-back produces one request for that date. Stable repeating trigger matching during gaps/folds and time-zone changes while suspended is delegated to iOS and remains a physical-device check. No missed routine dates are queued as catch-up bursts. Existing exceptional custom date construction retains its prior JavaScript-compatible gap/fold resolution.

Rest Today persists only the current local-day preference and cancels remaining owned workout requests for that day; future selected days remain scheduled. It creates no workout, completion or streak credit. The workout destination offers it after a reminder tap, and the state refreshes on focus/foreground.

Automatic suppression from saved meals, imported/manual weight, paired BP, completed workouts or fluid goals is **deferred**. Stable native repeats were chosen for predictable operation when the app is suspended. This implementation does not claim to query current health data immediately before delivery, and it does not suppress from unsaved/stale data. The user's explicit allowance to ship predictable editable schedules first applies. Apart from Rest Today and existing custom completion behavior, notifications can still appear after activity has already been logged.

## Navigation, privacy and lifecycle

The Expo 57 response listener and synchronous startup-response API feed one persisted, validated intent. Known v2 payloads contain an owner ID, routine category/slot or custom reminder ID; no arbitrary URL, credentials, readings or calorie totals are used as navigation inputs. Legacy reminder IDs resolve only against a unique account-owned definition. Response identifier + delivery timestamp + action deduplicates startup/listener responses without suppressing tomorrow's tap from the same repeating request.

Intents expire 30 minutes after capture. Authentication errors/retries preserve them; explicit cancellation, expiry, incompatible account, deletion and successful consumption clear them. Routing waits for active foreground, initialized root navigation, completed account setup, successful authentication and privacy/Face ID unlock. A final account/unlock check after asynchronous consumption prevents a late auth/lock change from opening the destination. Known destinations are nutrition, water, track (BP), weight, workout and reminders. Old occurrence dates are never forwarded as logging dates. Meal preselection only fills an empty draft; an existing meal/date/entries remain intact. Opening a custom reminder never marks it taken.

Explicit logout/global sign-out cancels outgoing routine requests and pending navigation, preserving preferences. Account activation cancels other-account routines, restores the current account's enabled choices, and reconciles. Automatic session expiry does not erase reminder intent/settings, allowing a notification to resume login. Custom medication/logout behavior remains unchanged: its existing scheduled requests are not canceled by routine logout cleanup. Account deletion cancels all owned routine/custom/legacy pending requests, dismisses owned delivered notifications and clears pending intent before existing account-local data cleanup. No notification payload contains an auth credential.

## Amendment: independent reminders and medication schedules - 2026-09-23

This amendment supersedes the master-switch, first-activation wizard, quiet-hours, notification-count and retry-button UI described above.

- Meals, Fluids, Blood Pressure, Weight and Workout each enable independently. Medication / Supplements is a sixth entry opening a dedicated list; every medication/supplement has its own name, enable switch and schedule. There is no extra medication group master switch. Existing medication/supplement definitions move into this view by their structured kind, retaining IDs and completion history. Existing custom BP/weight records remain accessible; new Custom Reminders begin with a blank name and cannot create those dedicated kinds.
- Routine payload version 2 removes enabled/configured/quiet fields. The existing account-scoped v1 storage key is retained for cleanup/export compatibility. Strict reads upgrade version-1 payloads: each effective enabled state is old master AND category enabled, preserving chosen days, times, rest-day and replacement/history references. Old master-off preferences never unexpectedly activate notifications. New saves persist version 2. Quiet hours have no validation or scheduling effect.
- All reminder editors, the medication list and overlap decisions opt into the shared SettingsSheet full-screen mode, with safe-area spacing, fixed header, keyboard avoidance and scrollable content. Other Profile sheets retain their original presentation. Slot switches sit centered alongside the full time card. The main screen removes quiet hours, routine-per-day counts, Retry scheduling, local-device copy and the Custom Reminders explanatory message.
- Recurrence and times are independent: daily, selected days, weekly and every-N-days reminders allow up to six distinct local times. Every-N-days accepts whole intervals from 2 through 365 and an explicit start date. A UTC calendar-date ordinal is used only to count days modulo the interval; actual delivery dates are constructed at the selected local wall-clock time. This avoids fixed-duration DST drift. Existing multiple_daily definitions remain readable. Per-time completions also apply to selected-day and interval schedules; historical reminder streak evaluation excludes interval off-days.
- Stable daily/weekly schedules retain native calendar repeats. Every-N-days uses the next 14 valid dated occurrences, replenished by the existing foreground/account/edit reconciliation. This is a bounded occurrence window, not indefinite background rescheduling; the editor asks users to open HealthApp regularly to refresh it. The existing shared capacity checks, verified replacement and explicit failure reporting still apply. No remote push service, background timer, backend schema change or native dependency was added.
- Verification: 35 focused reminder tests; full root lint/TypeScript plus 235 app / 66 Edge tests; nine reminder browser cases and five Profile regression cases; iOS/Hermes export. Browser cases cover every routine editor's full-screen dimensions, centered slot switches, independent toggles, night times, multiple medication/supplement definitions, selected-day multi-time schedules, interval validation, persistence across re-login, simplified Custom creation, overlap-history protection and compact dark enlarged-text layout. Actual iPhone keyboard, accessibility and OS delivery remain physical-device checks.

## Amendment: Track entry and medication category toggle - 2026-09-23

The latest requested design replaces the preceding no-group-switch choice with a Medication / Supplements category toggle. The additive medicationEnabled preference defaults true when absent to preserve legacy schedules. Effective scheduling masks medication/supplement enabled flags while the group is off; stored individual choices and completion history are preserved, and other custom reminders remain unaffected. The same effective set drives explicit cancellation, legacy retention, native planning and replacement reconciliation. Enabling a group without items opens setup.

Track is the visible reminder entry point; the Profile link is removed and its old route redirects. Reminder settings remain full-screen, with a centered Cancel/Delete popup above the editor. The routine subheader and scheduled-success paragraph are removed; the Custom add action is grouped directly below its heading/list. The bounded workout/interval scheduling horizons described above remain unchanged. Service tests, 17 browser cases and an iOS export validate this refinement locally; native-device validation remains open.

## Amendment: persistent medication modal - 2026-09-23

The medication list and custom/medication editor now share one persistent full-screen Modal. SettingsSheet can render embedded content so navigation swaps the list and editor without dismissing to the underlying Reminders screen. This avoids the native dismiss/present gap while retaining the shared safe-area, keyboard and privacy behavior. The host forwards native back/escape to the editor's existing close guards; unsaved changes still require a discard decision. Other SettingsSheet callers keep their existing presentation.

Custom and medication deletion use the saved-food confirmation spacing and shared action buttons. Browser regressions assert stable modal identity through add/edit/save/cancel/delete, draft preservation and add-button label centering. All 17 reminder/Profile cases, root checks and iOS export pass; browser continuity and export do not certify physical-iPhone animation.
